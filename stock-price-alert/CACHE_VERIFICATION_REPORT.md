## 📊 深度分析

### 为什么改善如此显著？

选股流程中，每只股票需要：
1. **评分** - 调用 `_load_df_cached(code)` 获取 60 days K线
2. **回测1年** - 调用 `_load_df_cached(code, lookback=250)` 获取 250 days K线
3. **回测3年** - 调用 `_load_df_cached(code, lookback=750)` 获取 750 days K线
4. **回测5年** - 调用 `_load_df_cached(code, lookback=1250)` 获取 1250 days K线

**缓存命中**：
- 第1次运行：每个参数组合都要调用 API → 数据库查询 → 数据返回
- 第2次运行：60个参数组合全部命中 LRU 缓存 → 内存直接返回（<1ms）

```
第1次: 60只 × 4个lookback参数 = 240次 API 调用
第2次: 240次都命中缓存 = 0次 API 调用
```

**时间分解**：
- 第1次中，60个样本 + API 限流 = 52.6s
- 第2次中，60个样本 + 缓存 = 5.4s（主要是串行 I/O）
- **差异 47.2s** 全部来自缓存命中

## 💡 关键发现

### 1. 为什么单独测试 vs 完整场景差异这么大？

```
单独测试 (4.1% 改善):
  - 只做 2轮（冷启动 + 热启动）
  - API 调用时间 >> 缓存时间
  - 收益被初始化成本淹没

完整场景 (89.7% 改善):
  - 60只股票，4个 lookback 参数 = 240次调用
  - 第2次全部命中缓存
  - API 调用时间 << 缓存时间
  - 收益充分体现
```

### 2. 缓存的关键作用

```
关键 1: 同一轮选股中重复调用
  - 评分需要 60d, 回测需要 250/750/1250d
  - 这些 lookback 参数不同但**同一只股票**
  - LRU 按 (code, lookback) 建立 key，每个组合都缓存

关键 2: 多轮选股之间的重复
  - 第1次选股: 从数据库拉取 60只 × 4个参数 = 240次
  - 第2次选股: 同样的 60只、同样的参数 = 100% 缓存命中
```

### 3. LRU 设计的优势

```
vs 手工字典缓存:
  ❌ 手工字典: 无限增长，内存泄漏风险
  ✅ LRU:      自动清理 300只，防止内存爆炸
  
vs 其他缓存:
  ✅ 无需外部依赖 (functools 内置)
  ✅ 线程安全 (CPython GIL 保证)
  ✅ 低开销 (哈希查询 O(1))
```
