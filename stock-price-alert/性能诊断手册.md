# 半小时级轮询耗时 — 诊断手册（不改代码）

> **适用**：单轮明显偏慢（例如十几分钟～半小时），希望**只改配置、先看终端**判断瓶颈；精确毫秒仍以 JSONL 为准。  
> **说明**：主循环每轮结束会在终端打印 **`[轮询完成] 耗时 x.xx s`**（与 JSONL 中 `event=poll_round_done` 的 **`duration_ms`** 同源），见 `观测与性能说明.md`。

---

## 第一步：核对三个最影响耗时的配置

打开 `config.json`（未写明的项以 `merge_full_config` / `config.example.json` 中的默认为准）。

| 配置项 | 建议（快速） | 危险（易拖慢） |
|--------|----------------|----------------|
| `performance.request_min_interval_sec` | `0` 或 `0.05` | **≥ 0.5**（越大越慢） |
| `performance.kline_cache_ttl_sec` | **≥ 900**（合并默认） | **小于 60**（易重复打日 K） |
| `performance.sector_kline_cache_ttl_sec` | **≥ 3600**（合并默认） | 过小则板块日 K 重复请求 |
| `kline_store.enabled` + 盘后同步 | `true`，且每日盘后跑 `sync_daily_klines.py` | `false` 或 DB **不新鲜**（仍大量走网络日 K） |

若 **`data_health.enabled=true`** 且某主机（域名）**连续 HTTP 失败**达到计数，`data_health.extra_backoff_sleep_sec` 会在 **`utils.safe_get` 每次请求前**额外 `sleep` 一段指数退避（受 `backoff_base_sec`、`backoff_cap_sec` 限制，**上限可达数秒级**）。网络抖动或东财不稳定时，这部分会**与随机 1～3 秒、全局限流等叠加**，进一步拉长单轮耗时。

**实现细节（避免误解）**：

- `request_min_interval_sec` 作用在 **`utils.safe_get`** 上（东财日 K 等），**不是**每一个进程内 HTTP；多源现价等走 `requests_get_with_health` 的路径不受该间隔约束。
- `kline_cache_ttl_sec` 过小：同一轮或相邻轮内更容易 **miss RAM 缓存**，日 K 反复 `safe_get`；`safe_get` 另有 **每次约 1～3 秒随机等待**（与该项无关），会进一步放大墙钟时间。

## 第二步：单轮观察控制台「来源」

执行：

```bash
python run_alert.py --once --no-notify
```

在每只标的块里查找（文案以实际输出为准）：

| 行（示意） | 含义 |
|------------|------|
| `└ 现价来源：realtime_hub` | 较好：主循环优先用 Hub 缓存的现价，减少与主拉取重复的现价 HTTP。 |
| `└ 现价来源：eastmoney`（或其它非 hub） | 说明本轮该票现价仍走了网络路径；若**多数**如此，检查 Hub 是否启用、首轮是否尚未暖机。 |
| `└ K 线数据：ram_cache` / `sqlite` | 较好：日 K 来自内存 TTL 或本地库。 |
| `└ K 线数据：network` | 日 K 仍走东财网络；若**多数**如此，检查 TTL、`kline_store` 与库新鲜度。 |
| `└ 趋势板块柱 BK：BKxxxx` | 板块 BK 已解析；若出现缺板块、两柱退化等提示，多为**数据/映射**问题，对耗时的影响通常不如大量 `network` 日 K。 |

**统计比例（目测即可）**：

- **过半** `现价来源` 非 hub：Hub 命中差，每票多一段现价类请求成本。  
- **过半** `K 线数据：network`：日 K 缓存或本地库未发挥作用，轮询会明显变慢。

**板块日 K 是否已取到（终端间接判断）**：

- 若出现 **`└ 趋势板块柱 BK：BKxxxx`**，且**没有**随后打印「**板块K线缺失** / 未计板块柱」一类退化提示，可认为**板块日 K 已成功参与计算**（数据来自东财网络或 RAM/SQLite 缓存之一，与个股日 K 同源字段）。
- 当前实现**未**在 JSONL 顶层写入名为 `sector_kline_source` 的字段；板块侧与个股一致，在内存结构 `pack["sector_kline"]` 里使用 **`kline_data_source`**（如 `network`、`ram_cache`、`sqlite`）。若要**精确**看到该值，需临时调试打印、或后续在产品里为终端/JSONL 增加一行展示；开启 `logging.enabled` 后，现有 `watch_*` 行也**不一定**包含板块 K 的 `kline_data_source`，请勿假定 JSONL 里必有 `sector_kline_source`。

## 第三步：粗算理论墙钟量级

记本轮实际参与拉取的标的数为 **N**（与控制台分组里出现的只数一致即可）。

对单只票粗估「仍占 `safe_get` 类慢路径」的次数 **R**（**经验刻度**，非严格代码计数）：

- 现价未走 Hub、仍打网络：**R +≈ 1**  
- 日 K 为 `network`：**R +≈ 1**（每次成功/失败还可能多 host 回退，实际常大于 1）  
- 板块日 K：终端无直接来源行时，可按「有 BK 且未报板块 K 缺失」认为多数已拉到；若大量解析失败，对耗时的影响因路径而异，此处不强行加 0.5。

每次慢路径请求的综合耗时 **T**（网络 + `safe_get` 内随机等待 + **`data_health` 退避** + 重试）：粗算可取 **1.5～4 秒** 量级（退避大时可更高），勿当精确常数。

并行度取 **`performance.fetch_max_concurrency`（默认 3）**。

**粗公式（数量级）**：

```text
墙钟 ≳ (N × R × T) / max(1, fetch_max_concurrency)
```

再叠加：**`request_min_interval_sec`** 会在每个 `safe_get` 之间强制排队，使上式结果**成倍**放大；**串行** `process_watch_pack`、SQLite 读锁争用等也会再加一截。

**例**：N=20，多数票 R≈2（现价网络 + 日 K 网络），T≈2s，并发 3 → 约 (20×2×2)/3 ≈ **27s** 仅下限量级；若 `request_min_interval_sec=0.5` 且每票多次 `safe_get`，**到十分钟级以上很常见**；N 更大或失败重试多时，可到**半小时量级**。这与「单一 bug」无关，多为 **配置 + 缓存命中 + 并发上限** 叠加。

## 结论与后续动作

通过上述三步，一般可判断：慢主要来自 **配置（尤其全局限流、TTL）**、**缓存/本地库未命中**，还是 **Hub 未分担现价** 或 **`data_health` 退避**；而不是必须先怀疑逻辑错误。

**按现象调配置时，请直接看下一节「按优先级调整配置」**（推荐顺序：**A → B → C → E → D**）。其中 **D（关 `data_health`）** 影响面最大，仅作权衡。

---

## 根据诊断结果按优先级调整配置

下列与手册前文「三步诊断」对应；修改 `config.json` 后保存，用 `python run_alert.py --once --no-notify` 复测。

### 情况 A：`request_min_interval_sec` 不为 0（最常见拖慢项）

| 现象 | 单轮几分钟～半小时；配置里 **`performance.request_min_interval_sec` ≥ 0.5**（或任意明显大于 0 的值）。 |
|------|------------------------------------------------------------------------------------------------------------|
| 处理 | 在 `performance` 下将 **`request_min_interval_sec`** 设为 **`0`**（关闭对 `safe_get` 的全局限流），或 **`0.05`**（约 50ms，仅缓和突刺）。 |
| 预期 | 往往最明显；**体感**常见为 **约减半～八成** 量级的缩短（随标的数、失败重试次数变化，非保证值）。 |

### 情况 B：大量 **`K 线数据：network`**（缓存 / 本地库未命中）

| 现象 | 控制台里多数票为 **`└ K 线数据：network`**。 |
|------|---------------------------------------------|

**B1. 增大内存 TTL（在可接受的数据陈旧度内）**

- `performance.kline_cache_ttl_sec`：合并默认 **900**；仍可酌情调高（如 1800）。  
- `performance.sector_kline_cache_ttl_sec`：合并默认 **3600**。

**B2. 启用并喂饱本地 SQLite 日 K**

- `kline_store.enabled`：**true**（与 `config.example.json` 一致）。  
- 每日盘后执行：`python sync_daily_klines.py`（见仓库脚本说明）。  
- `kline_store.fresh_hours_after_sync`：默认 **36**；保证盘后 **36 小时内** DB 视为新鲜，监控端优先 **sqlite** 路径，减少东财 `push2his`。

**预期**：日 K 大量变为 **`sqlite` / `ram_cache`** 后，单轮里日 K 相关墙钟可明显下降（极端理想下可接近「秒级 + 现价/板块余量」，仍取决于 N 与 Hub）。

### 情况 C：多数 **`现价来源：eastmoney`**（Hub 未命中）

| 现象 | 多数票为 **`└ 现价来源：eastmoney`** 等，而非 **`realtime_hub`**。 |
|------|---------------------------------------------------------------------|
| 处理 | ① **`realtime_hub.enabled`**：保持 **true**。② **`realtime_hub.poll_interval_sec`**：宜**小于**主循环的 **`poll_interval_seconds`**（例如主轮询 30s、Hub 5s）。③ **`performance.hub_poll_start_offset_sec`**（合并默认 **3**）：Hub 线程启动后先等待再拉首轮，与主循环首轮错开。④ 首轮 Hub 未暖机时，可先跑一次 **`--once --no-notify`** 再常驻监控。 |
| 预期 | 命中后每票少一段现价类 HTTP；收益随「原 eastmoney 占比」变化。 |

### 情况 D：`data_health` 退避频繁（网络差、失败多）

| 现象 | **`data_health.enabled=true`** 且失败多；`safe_get` 前会叠加 **`extra_backoff_sleep_sec`**（指数退避，受 `backoff_base_sec`、`backoff_cap_sec` 限制，**可达数秒**）。与 `[DATA_OUTAGE]`、主机告警等可能同时出现。 |
|------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

**说明（避免误调）**：**`host_consecutive_fail_threshold`** 主要用于「连续失败达阈」时的**日志 / 观测**（如 `data_health_host_threshold`），**不会**关掉「第一次失败后的退避」；退避在 **只要有主机失败计数** 时就会随 `extra_backoff_sleep_sec` 增长。

| 处理（择一，权衡风险） | ① **优先**：改善网络、提高缓存命中（见 A/B），减少失败次数。② **调小** `backoff_base_sec` / **`backoff_cap_sec`**，减轻单次退避上限（仍随失败次数指数增长，直至 cap）。③ **`data_health.enabled=false`**：去掉退避与主机失败计数逻辑（**同时**削弱与 P0-1 全失败、`suppress_trend_rounds_after_full_outage` 等**联动**，仅在网络极差且确认可接受时短期使用）。 |
|------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

### 情况 E：`fetch_max_concurrency` 偏低、标的很多

| 现象 | **`watchlist`（或 quality 池）** 明显多于 **20**，而 **`performance.fetch_max_concurrency`** 仍为默认 **3**。 |
|------|------------------------------------------------------------------------------------------------------------------|
| 处理 | 适度提高 **`fetch_max_concurrency`**（如 **4～6**），与 **`fetch_max_workers`** 配合（workers 不宜过小）。**注意**：东财侧不宜过高并发；若 **`kline_store` 读库** 占比高，**全局 `_DB_LOCK`** 可能让过高并发收益变钝，可先试 **4**。 |
| 预期 | 拉取阶段墙钟近似按「批次数」下降；与 A、B 叠加后更明显。 |

### 综合优化示例（按需合并进现有 `config.json`）

以下为 **合法 JSON**（勿写 `//` 注释）；请与文件中已有 `performance`、`kline_store`、`realtime_hub`、`data_health` 等**合并**，勿重复键。

```json
{
  "performance": {
    "enable_parallel_fetch": true,
    "fetch_max_workers": 4,
    "fetch_max_concurrency": 4,
    "request_min_interval_sec": 0,
    "hub_poll_start_offset_sec": 3,
    "kline_cache_ttl_sec": 900,
    "sector_kline_cache_ttl_sec": 3600
  },
  "kline_store": {
    "enabled": true,
    "db_path": "data/daily_klines.db",
    "fresh_hours_after_sync": 36
  },
  "realtime_hub": {
    "enabled": true,
    "poll_interval_sec": 5
  },
  "data_health": {
    "enabled": true,
    "host_consecutive_fail_threshold": 5,
    "backoff_cap_sec": 16,
    "backoff_base_sec": 0.25
  }
}
```

若确需**关闭** `data_health` 以去掉退避，将 **`"enabled": false`** 即可；请同时阅读 `待实现改进清单.md` / P0-1 与 **`技术设计说明-DeepSeek审阅.md`** 中 **`data_health`** 节，了解失去的联动。

**已在代码侧落实（`merge_full_config` 缺省键时与 `config.example.json` 对齐）**：`request_min_interval_sec=0`；`kline_cache_ttl_sec=900`、`sector_kline_cache_ttl_sec=3600`；`fetch_max_concurrency=4`；`hub_poll_start_offset_sec=3`（Hub 首轮与主循环错开）；`data_health.backoff_cap_sec=16`、`backoff_base_sec=0.25`；`kline_store.enabled` 默认 true；主循环每轮终端 **`[轮询完成] 耗时 x.xx s`**。若你的 `config.json` 仍写有旧值，以文件为准覆盖合并结果。

### 验证效果

1. 修改保存后执行：`python run_alert.py --once --no-notify`。  
2. **控制台**：目测 **`现价来源：realtime_hub`** 与 **`K 线数据：ram_cache` / `sqlite`** 占比是否上升。  
3. **墙钟**：直接看本轮末尾终端行 **`[轮询完成] 耗时 x.xx s`**；或从首行 **`===== 轮询 …`** 到该行之间手计。  
4. **精确毫秒**：`logging.enabled=true` 时，在 JSONL 中查 **`event=poll_round_done`** 的 **`duration_ms`**（与上句同源）。

在 **A + B + C** 同时到位、N≈20 的常见场景下，**从半小时量级降到约数十秒量级** 是合理目标；**非承诺**，仍受网络、退避、板块解析等影响。

---

### 若仍然慢

1. **网络**：本机到东财相关域名延迟/丢包（如 `push2his.eastmoney.com`）。  
2. **监控只数**：减少 `watchlist` / 优质池监控数量，只保留必要标的。  
3. **轮询频率**：根配置 **`poll_interval_seconds`**（盘中秒数）从 30 提到 **60** 等，降低**单位时间**请求次数（**不**缩短单次 `--once` 轮内的拉取时间，但减轻全天总负载）。

## 补充：已落地的性能相关改动（2026-04-30）

1. **`sync_daily_klines.py`**：在原有「全表 `watchlist` + 板块 BK」基础上，默认再并入 **`daily_picks.json` 优质股列表**中的代码（及对应用 `resolve_sector_bk` 解析的板块日 K），与盘中 **`quality_only`** 模式下「优质池里不在 config watchlist 的代码」对齐，减少这些标的日 K 仍显示 **`network`**。仅需 watchlist 时加 **`--skip-daily-picks`**。合并后 secid 数量会明显增加，全量同步耗时变长属正常，可配合 **`--progress-every`**。
2. **`realtime_hub` + `run_alert`**：Hub 启用时，每轮在 **`hub.set_watch_rules(watch)`** 之后调用 **`wait_for_quote_coverage`**，在 **`performance.hub_warm_timeout_sec`**（默认 12）秒内等到至少 **`hub_warm_min_fraction`**（默认 0.85）的标的在 Hub 缓存中有有效现价，再开始并行拉包，缓解 **`hub_poll_start_offset_sec`** 与首轮并行之间的竞态，减轻「**现价来源全是 sina**」的首轮现象。
